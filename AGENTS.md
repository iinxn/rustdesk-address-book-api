# AGENTS.md — правила работы с rustdesk-ab-backend

Это краткая обязательная точка входа для AI-агента и разработчика. Подробности
лежат в тематических документах; не превращай этот файл в энциклопедию.

## Что это за проект

Self-hosted backend для **немодифицированного** клиента RustDesk:

- RustDesk-совместимый API адресной книги `/api/*`;
- внутренний JSON API панели `/api/v1/*` и React SPA `/app/`;
- legacy server-rendered панель `/panel/`;
- KX-shim на TCP/UDP `21116`, который завершает server-first `KeyExchange`
  для залогиненных клиентов и проксирует трафик в настоящий OSS `hbbs`.

Один процесс `python -m app` поднимает FastAPI, применяет миграции Alembic,
запускает супервизор шима и фоновый drain discovery-событий. Одна SQLite-БД
(по умолчанию `data/base.db`). Проект **не заменяет** `hbbs`/`hbbr` и не
реализует relay.

## 1. Технические инварианты

Нарушение этих пунктов почти всегда является багом:

1. **Клиент не патчится.** Формы ответов `/api/login`, `/api/ab/*`,
   `/api/heartbeat`, `/api/sysinfo` — контракт со штатным RustDesk. Меняй их
   только при доказанной несовместимости и с проверкой на живом клиенте.
2. **`/api/v1/*` — внутренний API панели.** Расширенные поля (`presence`,
   `tag_objs`, `info`, `in_books`, счётчики) не должны протекать в
   RustDesk-совместимые ответы без необходимости.
3. **Права книг:** `rule` 1 = read, 2 = readWrite, 3 = fullControl.
   `can_write(rule)` — это `rule >= 2`. Персональная книга принадлежит
   владельцу; shared-книга доступна по `address_book_permissions`, админ
   видит все shared-книги. Проверка прав выполняется на каждом запросе.
4. **Одна БД, Alembic — единственный способ менять схему.** Не удаляй,
   не пересоздавай и не «чини» рабочую БД. Не меняй `alembic_version`
   вручную. Новая миграция должна быть в git: Docker/клон собирают только
   закоммиченные файлы. **Фактическое состояние:** `Dockerfile`,
   `docker-compose.yml` и `.dockerignore` сейчас в `.gitignore`; не обещай
   Docker-деплой с чистого клона, пока это не исправлено.
5. **Шим — отдельный сетевой компонент.** `SHIM_LISTEN` — адрес bind,
   `SHIM_UPSTREAM` — rendezvous-порт настоящего `hbbs` (не relay `21117`),
   `SHIM_ID_KEY` — приватный 64-байтный `id_ed25519`. Шим не аутентифицирует
   клиентов на уровне протокола; защита — лимиты и сеть.
6. **Секреты не попадают в git, логи, ответы и документацию.** Не печатай
   `DEVICE_SECRET`, `WEB_SECRET`, токены, пароли, приватные ключи и
   содержимое `.env`. В логах шима допустимы только отпечатки.
7. **Приватные сети и реальные адреса не документируются.** В примерах
   используй `<hbbs-host>`, `203.0.113.10`, `example.lan` и т. п.
8. **Часовые метки — naive UTC** (`datetime.utcnow()`), так исторически
   устроена схема. Не начинай «исправлять» это точечно: либо миграция всех
   слоёв, либо явная обработка на границе (frontend `parseUtc`).
9. **Ошибки не маскируются.** Не увеличивай таймаут и не добавляй retry,
   пока не понятна причина. Не считай проблему решённой, если сообщение
   просто перестало отображаться.

## 2. Перед началом задачи

1. Прочитай этот файл и `docs/TODO.md`; определи, есть ли уже задача с такими
   критериями готовности и не противоречит ли новая работа текущим
   приоритетам.
2. Определи затронутые компоненты: API, сервисы, модели, миграции, shim,
   frontend, Docker/скрипты.
3. Открой соответствующий раздел `ARCHITECTURE.md` и `REPOSITORY_MAP.md`.
4. Проверь `ERRORS.md` и `LESSONS_LEARNED.md` на похожие симптомы.
5. Изучи фактическую реализацию и git-историю до изменения кода.
6. Проверь совместимость с существующими данными и клиентским контрактом.
7. Если задача меняет поведение, сначала сформулируй проверяемый сценарий
   «до/после»; не делай несколько несвязанных изменений одновременно.

## 3. Диагностика

1. Сначала факты: воспроизведи ошибку, собери точный текст, версию, условия.
2. Проверь `/health/ready`, порты, конфигурацию, БД и логи источника.
3. Ищи причину, а не симптом. Для shim отделяй TCP KX, UDP relay, upstream
   `hbbs`, ключи и сетевую доступность.
4. Проверь, не было ли это уже исправлено/опровергнуто: `ERRORS.md`,
   `LESSONS_LEARNED.md`, `git log`.
5. Не повторяй отклонённые решения без новых данных.
6. После изменения проверь побочные эффекты: права книг, presence,
   discovered, sysinfo, миграции, frontend-контракт.
7. Не оставляй после себя запущенные процессы, временные БД и изменённые
   `data/`, `logs/`, `.env`, если это не часть задачи.

## 4. Изменение кода

- Следуй существующей структуре: routers в `app/api/`, бизнес-логика в
  `app/services/`, модели в `app/models/models.py`, настройки в
  `app/core/config.py`.
- Не добавляй зависимости без необходимости. Новые библиотеки — только с
  обоснованием и проверкой Docker-совместимости.
- Сохраняй обратную совместимость API. Новые поля в ответах добавляй
  осторожно; удаление/переименование полей — ломающее изменение.
- Не логируй секреты и персональные данные. Не добавляй `print` в рабочий код.
- Для ошибок API соблюдай формат компонента: RustDesk-роуты — `{"error": ...}`,
  `/api/v1` — `{"detail": ...}`. Не смешивай без причины.
- Не используй `dangerouslySetInnerHTML`; Jinja-шаблоны уже автоэкранируются.
- Для SQLite используй ORM/параметризованные запросы; не собирай SQL из
  пользовательских строк. Сортировки/фильтры — только из белого списка.

## 5. Схема SQLite и постоянные данные

Перед любой правкой схемы прочитай `docs/project/DATA_MODEL.md` полностью.

- Новая миграция: `alembic/versions/NNNN_<name>.py`, `down_revision` — текущий
  head; `upgrade()` и `downgrade()`; для SQLite-изменений колонок/ограничений
  используй `op.batch_alter_table`.
- Миграция должна быть **идемпотентно применима к существующей БД** и
  проверена на копии реальной БД, а не только на пустой.
- Аддитивные изменения (новые таблицы/колонки) безопаснее; удаление и
  переименование — только с планом совместимости и backup.
- Перед экспериментами: `python -m app.cli backup` или копия файла БД.
  Проверяй `PRAGMA integrity_check`.
- Никогда не советуй «удалить базу и накатить заново» как штатное решение.
- Помни: `data/base.db` и `data/pc-service.db` могут содержать разные
  исторические данные. Не переключай `DATABASE_URL` и не сливай их без
  явного решения владельца.

## 6. Тесты и проверки

**Фактическое состояние:** автотесты есть для heartbeat rate limiting и
sysinfo write-once (`tests/test_heartbeat_rate_limit.py`,
`tests/test_sysinfo_upload.py`, временная SQLite + Alembic). Полного покрытия
нет; `pytest`/`httpx` живут в `requirements-dev.txt`, не в runtime. Не
заявляй, что тесты пройдены, если ты их не запускал, и не выдавай один набор
за покрытие всего проекта.

Минимальные проверки для любой задачи:

```bash
# синтаксис/импорт Python (с текущим .venv)
.venv/bin/python -m compileall -q app tests
.venv/bin/python -c 'import app.main'

# автотесты
.venv/bin/python -m pytest -q

# frontend (если менялся UI/контракт)
cd frontend && npm run build && npm run lint
```

Плюс ручной smoke-тест из `docs/development/TESTING.md`: `/health/ready`,
логин, `/api/ab/personal`, нужный сценарий, для shim — `secure established`
или `plain passthrough`. Если тесты добавляются — они должны использовать
временную БД/`tmp_path`, а не `data/`.

## 7. Безопасность

Перед изменениями в auth, сети, деплое или обработке ввода прочитай
`docs/SECURITY.md`.

- Не отключай проверки ради удобства. TLS terminates на прокси; приложение
  само по себе отдаёт HTTP.
- Панель и API не должны быть публичными без явного решения владельца.
  `/api/sysinfo`, `/api/heartbeat`, `/api/login-options` неаутентифицированы
  by design — это не повод добавлять туда доверенные данные.
- Не доверяй `X-Forwarded-For`, если прямой peer не входит в
  `TRUSTED_PROXIES`.
- Не раскрывай traceback, пути, SQL и секреты в ответах.
- Не добавляй CORS «на всякий случай»: SPA same-origin.
- При обнаружении уязвимости опиши её в `docs/SECURITY.md` и, если это
  воспроизводимая ошибка, в `ERRORS.md`; не копируй секреты.

## 8. Документация как часть задачи

Обновляй знания в той же задаче, а не «потом»:

- новая/повторяющаяся ошибка → `docs/knowledge/ERRORS.md`;
- важный вывод, который предотвращает повторение → `LESSONS_LEARNED.md`;
- архитектурное решение/компромисс → `DECISIONS.md`;
- изменение API/схемы/поведения/команд → `docs/project/*` или
  `docs/development/*`;
- изменение модели угроз → `docs/SECURITY.md`;
- состояние работ и следующие шаги → `docs/TODO.md` (обновляй статус после
  проверки критериев, не превращай файл в журнал).

Не дублируй один и тот же текст в нескольких файлах: дай ссылку. Не
выдумывай инциденты, коммиты и результаты тестов. Если факт не проверен,
пометь «требует проверки».

## 9. Завершение задачи

В отчёте укажи:

1. какие файлы созданы/изменены;
2. что проверено и какими командами;
3. что не удалось проверить и почему;
4. какие документы/записи обновлены;
5. остаточные риски и пробелы.

Обнови `TODO.md`: закрой выполненное, добавь новое, зафиксируй блокеры и
следующий шаг. Не отмечай задачу `[x]` без проверки критериев.

Не коммить изменения, если пользователь явно не попросил. Не оставляй
секреты в выводе команд и в новых файлах.
