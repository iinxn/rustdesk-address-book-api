# SECURITY — модель доверия, ограничения и реестр

Документ фиксирует **фактическую** модель безопасности. Исторический аудит с
доказательствами и сценариями повторного тестирования — `SECURITY_AUDIT.md`
(2026-10-16, не в git). Здесь — актуальные статусы, решения и правила
эксплуатации. При расхождении приоритет у текущего кода; расхождение
описывай в этом файле, а не замалчивай.

## 1. Что защищаем

| Актив | Где | Почему важен |
|---|---|---|
| Учётные данные пользователей | `users.password_hash` (bcrypt) | вход в API/панель |
| Bearer-сессии | `sessions.token` (opaque) | доступ к книгам без пароля |
| Адресные книги | `address_books`, `address_book_entries` | чужие устройства/заметки |
| Пароли устройств | `password_encrypted` (Fernet), `hash_value` | доступ к управляемым ПК |
| Discovery-данные | `discovered_devices` | кто и откуда подключался |
| Sysinfo | `device_info` | hostname/username/OS/IP |
| Ключ `hbbs` | `SHIM_ID_KEY` | подпись server-first `KeyExchange` |
| Секреты приложения | `DEVICE_SECRET`, `WEB_SECRET` | расшифровка паролей, подпись cookie |
| Файл БД и backup | `data/*.db` | всё вышеперечисленное |

## 2. Акторы и границы доверия

| Актор | Возможности | Доверие |
|---|---|---|
| RustDesk-клиент (штатный) | `/api/*`, TCP/UDP `21116` | не доверяем; ID/поля валидируются |
| Залогиненный пользователь | свои книги + shared по `rule` | ограниченное; права проверяются на каждом запросе |
| Admin | все shared-книги, пользователи, discovery cleanup | высокое, но не безграничное (нельзя удалить/disable себя) |
| SPA в браузере | `/api/v1/*` с Bearer из `localStorage` | XSS = кража токена |
| Legacy-панель | cookie `session` | CSRF-риск, `https_only=False` |
| Локальный пользователь хоста | файлы `.env`, `data/`, `keys/` | зависит от прав; сейчас не везде 600 |
| Сеть между клиентом и API | HTTP | не доверяем; TLS только на прокси |
| Сеть между shim и `hbbs` | HTTP-нет, TCP plaintext protobuf | должен быть loopback/LAN/доверенный |
| UDP-источник | spoofable | не доверяем; только лимиты |

Ключевой принцип: **клиент не является доверенным**. `rustdesk_id`,
`book guid`, `rule`, `is_admin`, `owner` никогда не принимаются из тела
запроса как истина; они перепроверяются по БД.

## 3. Сетевая экспозиция

| Порт | Кто слушает | Что снаружи | Защита |
|---|---|---|---|
| `8000` (или `21114`) | FastAPI | API + SPA + legacy | Bearer/cookie, rate limit, body cap; **TLS только на прокси** |
| `21116/TCP` | shim | KX/plain proxy | caps, таймауты, нет auth по протоколу |
| `21116/UDP` | shim | rendezvous relay | caps, idle 120 с, plaintext |
| `21117` | **не проект** | relay `hbbr` | не публикуется и не проксируется |
| `21114` в Docker | **не публикуется** | — | нужен явный маппинг/`api-server` |

Приложение слушает то, что задано в `HOST`/`SHIM_LISTEN`; оно не знает,
VPN это или интернет. «API только через WG» кодом **не enforced**.

Рекомендуемая схема: API — loopback + reverse proxy с TLS; `21116` — только
из доверенной сети/по firewall; панель — не в публичный интернет без
аутентификации и TLS; `hbbs` — отдельно, upstream только с доверенного
сегмента.

## 4. Аутентификация

### 4.1. Bearer (клиент и SPA)

- `POST /api/login` → bcrypt-проверка → `secrets.token_urlsafe(32)` →
  строка в `sessions`; срок `SESSION_DAYS` (30 по умолчанию, `0` = никогда).
- Токен opaque, не JWT; подписи нет, проверка — поиск в БД.
- `user_by_token` проверяет expiry и `is_disabled`; просроченный токен
  удаляется.
- Logout удаляет строку. Disable и смена пароля удаляют **все** сессии
  пользователя.
- SPA хранит токен в `localStorage` (`ab_token`), не в памяти. Это осознанный
  компромисс: XSS приводит к краже токена; HttpOnly-cookie не используется,
  потому что SPA и API same-origin, но cookie-путь имеет свои CSRF-риски.

### 4.2. Cookie (legacy `/panel/`)

- Starlette `SessionMiddleware`: подпись `WEB_SECRET`, `SameSite=Lax`,
  `https_only=False`, срок по умолчанию 14 дней.
- `panel_user` проверяет `is_disabled` и очищает cookie; удалённый
  пользователь теряет доступ.
- CSRF-токенов нет. `SameSite=Lax` блокирует cross-site POST с cookie, но не
  покрывает same-site/поддоменные сценарии.
- Cookie живёт независимо от Bearer: logout из SPA не очищает panel-cookie
  и наоборот.

### 4.3. Что не реализовано

2FA/TFA, `verificationCode`, привязка к устройству, OIDC/LDAP, API-ключи
для интеграций, client certificates. Поля принимаются, но не проверяются —
не считай их защитой.

## 5. Авторизация книг

Единственный источник — `app/services/ab.py`:

- personal: доступ только владельцу, `rule=3`;
- shared: доступ при наличии `address_book_permissions`; `rule` из строки;
- admin: доступ ко всем shared, `rule=3`;
- иначе `get_book_for_user=None`, `rule_for=0`.

`can_write(rule) = rule >= 2`; rename/delete shared-книги — `rule >= 3`.
Проверка выполняется на каждом запросе, включая bulk (для каждого ID
отдельно). Ошибка доступа к чужой записи в `/api/v1` часто маскируется под
`404`, чтобы не раскрывать существование.

Ограничения:

- Нет API управления permissions: строки `address_book_permissions` создаются
  вне панели. Это функциональный пробел, а не дыра.
- `MAX_PEER_ONE_AB=0` по умолчанию = безлимит; `/api/v1/create_entry` лимит
  не проверяет (SEC-006 связан).
- Admin не может снять admin с себя, disable себя или удалить себя — защита
  от самоблокировки, но нет защиты от «последнего админа»: два админа могут
  друг друга удалить.

## 6. Секреты

| Секрет | Формат | Где | Компрометация |
|---|---|---|---|
| `DEVICE_SECRET` | Fernet key (44 символа) | `.env` / env / `.secrets.env` | расшифровка паролей устройств |
| `WEB_SECRET` | 32+ случайных символов | `.env` / env / `.secrets.env` | подделка panel-cookie |
| `SHIM_ID_KEY` | приватный 64-байтный `id_ed25519` | файл `keys/` | подделка сервера для клиентов, доверяющих этому ключу |
| `sessions.token` | opaque | БД | доступ к книгам |
| пароли устройств | Fernet-шифр | БД | доступ к ПК |

Правила:

- Не коммитить `.env`, `keys/`, `data/`, `*.db`, `*.log`, `.secrets.env`.
- `.env` и `.secrets.env` — `600`, владелец — сервисный пользователь.
  **Фактическое состояние на проверенной машине:** `.env` — `664`,
  `data/.secrets.env` — `664`, `data/pc-service.db` — `664`; `data/` — `700`,
  `data/base.db` — `600`. Это SEC-002: исправить `chmod 600` (каталог `700`
  частично компенсирует, но backup/копия/перенос — нет).
- Docker entrypoint сохраняет автосекреты в `/app/data/.secrets.env` (600) и
  переиспользует их. Удаление файла при пустых env = новые секреты.
- Логи: только отпечатки (8 hex) для ключей/KX; `SHIM_DIAG_MSGTYPES=1`
  логирует тип сообщения и target ID, не токены/ключи/пароли.
- В ответах API нет секретов; `/api/sysinfo` отбрасывает `uuid` и
  preset/option-поля, которые могут содержать пароли книг.
- `DEVICE_SECRET` нельзя ротировать без перешифрования: старые
  `password_encrypted` станут нечитаемыми (`decrypt_password` → `""`).
- `WEB_SECRET` можно ротировать: это разлогинит `/panel/`, Bearer-сессии
  останутся.
- `SHIM_ID_KEY` при компрометации меняют вместе с публичным ключом у клиентов;
  это не «перезапуск шима», а смена доверия.

## 7. Данные и SQLite

- Пароли пользователей — bcrypt, не обратимое шифрование.
- Пароли устройств — Fernet (AES-CBC + HMAC), ключ `DEVICE_SECRET`.
- `hash_value` — не пароль, а device hash из клиента; всё равно чувствителен.
- SQLite: `PRAGMA foreign_keys=ON`, `busy_timeout=5000`; ORM/параметризованные
  запросы; сортировки/фильтры из белого списка.
- `StaticFiles` монтирует только `frontend/dist`; `data/` наружу не отдаётся.
- Backup — `app.cli backup` (SQLite Backup API, `integrity_check`, `0600`).
  Backup-файлы не коммитить и хранить с теми же правами, что БД.
- Нет шифрования БД «at rest»: защита — права файла, диск/хост, backup.
- Нет audit log: изменения видны только по `updated_at`, автор не фиксируется.
- В `sessions` лежит сырой токен: компрометация БД = компрометация сессий.

## 8. Shim

- Shim **не аутентифицирует** клиентов на уровне протокола: это ограничение
  самого rendezvous-протокола. Защита — caps и сеть.
- TCP: server-first `KeyExchange`, подпись ключом `hbbs`; secure-режим —
  `crypto_box` + `secretbox` v0 (счётчики до использования, кадры ≤1 байта
  без шифра); plain-клиент проксируется без изменений.
- UDP: **plaintext**, без криптографии; source IP spoofable. Это не баг,
  а свойство протокола.
- Верхний предел: `SHIM_MAX_CONNS=200` одновременных TCP/UDP-сессий,
  `SHIM_PER_IP_PER_MIN=30` новых подключений/сессий с IP, frame cap 2 MiB,
  `READ_TIMEOUT=60`, `FIRST_TIMEOUT=40`, UDP idle 120 с + sweep 30 с.
- Discovery: парсятся только `register_peer`/`register_pk` до 4096 байт;
  новый ID на IP — `DISCOVERY_NEW_IDS_PER_IP_PER_MIN=30`; известный ID
  бесплатен 1800 с; очередь 20 000 событий, при переполнении дроп.
- Upstream фиксирован конфигом; клиент не может выбрать произвольный
  upstream. Relay `21117` не поддерживается.
- Супервизор: bounded backoff 1…60 с, `down` после >5 падений за 600 с;
  `/health/ready` → 503, но API продолжает работать.
- Ключевой материал не логируется; допускаются отпечатки.

Остаточные риски: DoS исчерпанием соединений/слоулорис в пределах caps;
UDP-спуфинг может искажать discovery/presence и нагружать relay; discovery
не является доказательством личности.

## 9. Браузер и HTTP

Реализовано:

- Jinja2 autoescape; React без `dangerouslySetInnerHTML`.
- Нет CORS-middleware (same-origin SPA) — это осознанно, не добавляй
  «на всякий случай».
- `/docs`, `/redoc`, `/openapi.json` отключены по умолчанию; включаются
  `DEV_MODE=1`/`EXPOSE_DOCS=1`.
- Ошибки без traceback/SQL/путей.
- `X-Forwarded-For` учитывается только от `TRUSTED_PROXIES`; иначе прямой IP.
- Rate limit на login/heartbeat/sysinfo; body cap 5 MiB.

Не реализовано:

- TLS внутри приложения (терминируется прокси).
- CSP, HSTS, `X-Frame-Options`, `X-Content-Type-Options`, `Referrer-Policy`.
- `TrustedHostMiddleware` (проверка `Host`).
- CSRF-токены для legacy-панели.
- HttpOnly-cookie для SPA (токен в `localStorage`).
- Защита от clickjacking.

Следствия: при XSS токен SPA крадётся; при HTTP токен/пароль/пароли устройств
идут открытым текстом; panel-cookie может уйти по HTTP; сторонний сайт может
встроить панель в iframe. Для production обязателен TLS-прокси и
минимизация доступа к панели.

## 10. DoS и ресурсы

- HTTP: rate limit только на login/heartbeat/sysinfo; остальные `/api/*` не
  throttled. Heartbeat — 20/мин на пару `(device id, client IP)` плюс
  агрегатный 6000/мин на IP; лимиты хранятся в памяти процесса, поэтому
  несколько uvicorn workers умножат их. Ответ `429` содержит `Retry-After`.
- `/api/sysinfo` — агрегатный 6000/мин на IP (нужен для первого старта парка:
  800 устройств шлют по одному отчёту). Write amplification ограничен
  отдельно: повторный отчёт для заполненной карточки не пишется, а строка
  для незнакомого ID не создаётся вовсе. Поэтому поток случайных ID не
  раздувает БД, несмотря на высокий сетевой лимит. Перезапись существующей
  карточки возможна только одноразовым разрешением из панели (120 с).
- `/api/ab/peers`: `pageSize` не капается, теги — N+1; большая книга грузит
  SQLite/GIL (SEC-006).
- `/api/v1/address-books/{bid}/entries`: фильтрация тегов/presence в Python
  после загрузки всех записей книги — память/CPU растут с книгой.
- Bulk: 500 ID за запрос; commit один, при ошибке rollback.
- Body cap смотрит только `Content-Length`; chunked без длины не
  ограничивается этим middleware (SEC-013). Uvicorn читает чанки, но
  приложение может накопить тело.
- Shim caps ограничивают TCP/UDP, но не делают сервис неуязвимым к
  распределённому флуду.
- SQLite single-writer: долгая запись блокирует остальные (busy_timeout 5 с).

## 11. Реестр SEC-001…SEC-020

Статусы на текущий код. «Исправлено» = проверено чтением кода; живого
повторного теста в этой задаче не было, если не указано иное.

| ID | Критичность | Статус | Суть и остаток |
|---|---|---|---|
| SEC-001 | HIGH | **Исправлено** | `panel_user` проверяет `is_disabled` и очищает cookie. Живой тест из аудита не перезапускался. |
| SEC-002 | MEDIUM | **Открыто** | `.env`/`.secrets.env`/`pc-service.db` имеют `664`; нужно `600`. `data/` `700` снижает риск, но не заменяет права файлов. |
| SEC-003 | MEDIUM | **Исправлено** | `TRUSTED_PROXIES` + `client_ip`; XFF игнорируется без доверенного peer. |
| SEC-004 | LOW/MEDIUM | **Открыто** | `int(color)` без валидации в `/api/ab/tag/add` и `/api/ab/tag/update` → 500 на нечисле/огромном значении. Панель ловит `ValueError`, API — нет. |
| SEC-005 | LOW | **Принято** | `/api/heartbeat` без auth может подделать presence любого ID. Ограничено 20/мин на `(id, client IP)` + 6000/мин суммарно на IP; чужой IP не расходует bucket устройства. `/api/sysinfo` тоже без auth: чужие данные можно записать только для известного панели ID и только пока карточка не заполнена; после этого нужна кнопка в панели. Закрыть нельзя без поломки протокола. |
| SEC-006 | LOW | **Открыто** | `/api/ab/peers` без капа `pageSize` + N+1 по тегам; `/api/v1/create_entry` не проверяет `MAX_PEER_ONE_AB`. |
| SEC-007 | MEDIUM | **Исправлено** | disable/смена пароля вызывают `destroy_user_sessions`; expired чистятся при login/use. |
| SEC-008 | LOW | **Исправлено** | docs/redoc/openapi отключены по умолчанию, флаг `EXPOSE_DOCS`. |
| SEC-009 | MEDIUM | **Открыто** | `config/Caddyfile.example` содержит plaintext `:8080` на тот же backend. Файл помечен diagnostic, но копипаст опасен. |
| SEC-010 | LOW | **Исправлено** | `stop.sh` проверяет PID/cwd/cmdline, ищет по `python -m app`, проверяет результат. |
| SEC-011 | INFO | **Исправлено** | дублированный `shim_max_conns` удалён. |
| SEC-012 | INFO | **Открыто** | naive UTC везде; frontend компенсирует `parseUtc`. Менять только целиком. |
| SEC-013 | LOW | **Открыто** | body cap только по `Content-Length`; chunked без длины обходит. |
| SEC-014 | LOW | **Исправлено** | `Gate.sweep` раз в 60 с + при admit; UDP sweep также чистит. |
| SEC-015 | LOW | **Исправлено** | `_tasks.add_done_callback(discard)`; `aclose` отменяет задачи. |
| SEC-016 | LOW | **Принято** | legacy POST без CSRF-токенов, только `SameSite=Lax`. |
| SEC-017 | MEDIUM при HTTP | **Открыто** | `https_only=False`, cookie 14 дней. Включать только вместе с TLS-прокси и флагом. |
| SEC-018 | INFO | **Принято** | секреты в env/compose видны через `docker inspect`/`/proc`; штатно для Docker, держать compose под 600. |
| SEC-019 | INFO | **Частично** | expired-сессии чистятся при login/use; фоновой задачи нет, `expires_at IS NULL` не удаляются. |
| SEC-020 | INFO | **Открыто** | `data/app.pid` предсказуем, TOCTOU в `stop.sh`; влияние ограничено локальным пользователем. |

## 12. Принятые риски

Явно приняты, пока владелец не решит иначе:

1. Heartbeat spoof (SEC-005) — иначе presence не работает для устройств без
   учётных данных. Лимит не делает presence доверенным источником.
2. Legacy-панель без CSRF (SEC-016) — same-site сценарий остаётся.
3. Секреты Docker в env (SEC-018) — штатная модель Docker.
4. Отсутствие auth на shim — свойство протокола; компенсируется caps/сетью.
5. UDP plaintext/spoofable — свойство протокола.
6. Нет audit log — осознанный MVP-компромисс.
7. `data/base.db` и `pc-service.db` не сливаются автоматически — данные
   владельца важнее «чистоты».

Не являются принятыми рисками и требуют исправления перед публичным
доступом: SEC-002, SEC-004, SEC-006, SEC-009, SEC-013, SEC-017 (вместе с
TLS), отсутствие security headers.

## 13. Чек-лист перед публикацией

- [ ] TLS-терминация на прокси; `8000` не опубликован напрямую.
- [ ] `TRUSTED_PROXIES` задан, если прокси на loopback.
- [ ] `DEV_MODE=0`, `EXPOSE_DOCS=0`.
- [ ] `.env`, `.secrets.env`, `*.db`, backup — `600`; `data/` — `700`;
      `keys/` — `700`, ключ — `600`.
- [ ] `SHIM_ENABLED` только если нужен; `SHIM_UPSTREAM` — rendezvous, не relay.
- [ ] Firewall: `21116` только из доверенной сети; панель — не в интернет.
- [ ] `SESSION_DAYS` и cookie max_age осознанно сокращены для hostile-сети.
- [ ] Пароли админов сильные; лишние пользователи disable/удалены.
- [ ] Backup проверен (`integrity_check`), хранится отдельно.
- [ ] Нет секретов в git, логах, Docker-истории, отчётах.
- [ ] Caddy-пример не скопирован с plaintext-блоком.
- [ ] Проверены `/health/ready`, логин, `/api/ab/personal`, нужный сценарий.

## 14. Реакция на инцидент

1. Зафиксируй факты: время, путь, IP, текст ошибки, что именно затронуто.
   Не копируй секреты.
2. Изолируй: останови публикацию портов/прокси, при необходимости останови
   приложение.
3. Отзови доступ: disable пользователя или удали его сессии; при подозрении
   на кражу cookie смени `WEB_SECRET`; при подозрении на утечку
   `DEVICE_SECRET` — перешифруй пароли; при утечке `SHIM_ID_KEY` — смени
   ключ и публичный ключ у клиентов.
4. Сохрани backup и логи (stdout/journal) для разбора; не «чини» БД
   вручную.
5. Проверь `sessions`, `users`, `address_book_permissions`, `discovered_devices`
   на аномалии.
6. Опиши воспроизводимую ошибку в `docs/knowledge/ERRORS.md`, а изменение
   модели угроз — здесь. Не публикуй секреты и реальные адреса.

## 15. Что не проверено

- Живой браузерный XSS/CSRF (нет Windows-стенда).
- TLS-конфигурация конкретного прокси.
- Поведение под длительной нагрузкой/гонками записи SQLite. Heartbeat и
  sysinfo проверены синтетически (800 устройств, 3200 heartbeat,
  первый старт и повторные upload-ы), но не на production-парке и не в
  течение часов.
- PostgreSQL-ветка.
- Полный brute-force в production-масштабе.
- Повторный прогон негативных тестов после security-фиксов; статусы
  «исправлено» основаны на коде, а не на новом живом прогоне.

Если факт не проверен, помечай его «требует проверки» — не выдавай за
доказанный.
