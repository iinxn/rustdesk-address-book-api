# DECISIONS — архитектурные решения и компромиссы

Зафиксированные решения, которые уже реализованы в коде. Формат:
**решение → контекст → следствия → что отклонено**. Это не список планов:
если решение изменится, запись нужно обновить, а не оставить «исторической».

## DEC-001. Shim вместо патча клиента и вместо RustDesk Server Pro

**Решение.** Отдельный KX-shim на `21116` завершает server-first
`KeyExchange` ключом `hbbs` и проксирует трафик в настоящий OSS `hbbs`.

**Контекст.** Залогиненный штатный клиент вызывает `secure_tcp()` и ждёт
server-first `KeyExchange`; OSS `hbbs` этого не делает, отсюда
`Failed to secure tcp: deadline has elapsed`. Патч клиента ломает
обновления и требование «немодифицированный клиент»; Pro-сервер — другая
редакция и лицензирование.

**Следствия.**
- Клиент остаётся штатным; обновления RustDesk не ломают схему.
- `hbbs` не патчится и не заменяется; shim — дополнительный сетевой
  компонент.
- Появляются ограничения протокола: shim не аутентифицирует клиентов,
  UDP plaintext, нужен приватный ключ `hbbs` и свободный `21116`.
- Secure-режим использует `crypto_box` + `secretbox` v0; состояние
  счётчиков и кадры ≤1 байта — часть протокола, не «оптимизация».

**Отклонено.** Форк клиента с отключением проверки; переход на Pro;
самописный relay. Причины — безопасность, совместимость, границы проекта.

## DEC-002. Bearer-сессии — opaque-токены в БД, не JWT

**Решение.** `POST /api/login` создаёт `secrets.token_urlsafe(32)` и строку
в `sessions`; проверка — поиск в БД, срок `SESSION_DAYS`.

**Контекст.** Нужен немедленный отзыв доступа (logout, disable, смена
пароля) и простая модель без ключей подписи.

**Следствия.**
- Отзыв мгновенный: удалили строку — токен мёртв.
- В БД лежит сырой токен: компрометация БД = компрометация сессий.
- Нет stateless-масштабирования; для одной SQLite-инсталляции это
  приемлемо.
- Disable и смена пароля вызывают `destroy_user_sessions`; expired
  чистятся при login/обращении.

**Отклонено.** JWT (нельзя отозвать без blacklist), cookie-only для SPA
(CSRF-риски), внешний identity provider.

## DEC-003. Личные и общие книги; `rule` 1/2/3

**Решение.** У пользователя одна personal-книга; shared-книги доступны по
`address_book_permissions.rule`: 1=read, 2=readWrite, 3=fullControl.
`can_write = rule >= 2`; rename/delete shared — `rule >= 3`; admin видит все
shared с `rule=3`.

**Контекст.** Нужно повторять семантику RustDesk Address Book и при этом
не давать администратору неявных прав на личные книги.

**Следствия.**
- Права проверяются на каждом запросе, включая bulk (для каждого ID).
- Personal-книгу нельзя удалить/переименовать через API книг.
- API управления permissions отсутствует — строки создаются вне панели.
  Это функциональный пробел, а не скрытая возможность.
- Ошибка доступа к чужой записи в `/api/v1` часто отдаётся как `404`.

**Отклонено.** Единая «командная» книга без прав; глобальный admin-доступ к
personal-книгам; ACL на уровне отдельного устройства.

## DEC-004. Одна SQLite-БД и Alembic как единственный способ миграций

**Решение.** По умолчанию `data/base.db`; схема меняется только
`alembic/versions/*`; `python -m app` применяет `upgrade head` при старте.

**Контекст.** Self-hosted MVP, один процесс, простая установка и backup.
SQLite достаточно для целевой нагрузки; PostgreSQL заявлен, но не проверен.

**Следствия.**
- Один writer; долгие bulk-операции блокируют записи (`busy_timeout=5 с`).
- Backup — `app.cli backup` (SQLite Backup API, `integrity_check`, `0600`).
- Миграция обязана быть в git: Docker/клон не увидят незакоммиченный файл.
- `data/base.db` и `data/pc-service.db` — разные исторические данные; их
  нельзя сливать/переключать автоматически.

**Отклонено.** `create_all()` вместо миграций; авто-пересоздание БД;
автоматический merge двух баз.

## DEC-005. Naive UTC во всех слоях

**Решение.** Все timestamps — `datetime.utcnow()` без timezone; отдача —
ISO 8601 без `Z`; frontend компенсирует `parseUtc`.

**Контекст.** Так исторически устроена схема и существующие данные.
Массовая миграция на timezone-aware timestamps затронула бы БД, API и
frontend одновременно.

**Следствия.**
- Любой новый код обязан писать naive UTC.
- Клиенты/скрипты, парсящие время, должны трактовать его как UTC.
- Точечное «исправление» в одном эндпоинте создаёт рассинхрон.

**Отклонено.** Постепенный переход «где удобно»; хранение локального
времени; добавление `Z` только в новых ответах.

## DEC-006. Discovery — побочный продукт shim, а не отдельный агент

**Решение.** Shim парсит `register_peer`/`register_pk` (до 4096 байт) и
складывает события в in-memory очередь; drain пишет в
`discovered_devices`.

**Контекст.** Нужно видеть ID, подключавшиеся к серверу, без настройки
`api-server` на клиенте и без установки агентов.

**Следствия.**
- Discovery работает даже без HTTP API на клиенте.
- Данные означают «шим видел ID», а не «это доверенное устройство».
- Очередь ограничена 20 000 событий; при переполнении события теряются.
- Stale-sweep обязателен на каждом цикле, иначе `online` «зависает».
- Новый ID с одного IP — 30/мин; известный ID бесплатен 1800 с.

**Отклонено.** Отдельный сканер сети; доверять sysinfo как discovery;
считать discovery доказательством личности.

## DEC-007. Sysinfo — строгий whitelist, без выдуманных полей

**Решение.** `/api/sysinfo` принимает только `hostname`, `username`, `os`,
`cpu`, `memory`, `version`, `id`; `uuid` и preset/option-ключи
отбрасываются. Парсинг CPU/RAM/OS консервативный: не распознал — пусто.

**Контекст.** Штатный клиент присылает ограниченный набор; preset/option
могут содержать пароли книг; UI не должен показывать выдуманные данные.

**Следствия.**
- В `device_info` нет GPU/диска/сетевой статистики — их просто нет в
  payload.
- Sysinfo требует настроенного `api-server` (или API на `21114`); discovery
  — нет.
- Refresh sysinfo — in-memory флаг на 30 минут, одноразовый, работает
  только если клиент шлёт heartbeat.

**Отклонено.** Хранить весь JSON «на всякий случай»; парсить поля
эвристиками и показывать догадки; создавать `device_info` из heartbeat.

## DEC-008. Legacy `/panel/` сохранена, новый UI — SPA `/app/`

**Решение.** Оставить серверную Jinja-панель как legacy-интерфейс; развивать
React SPA и `/api/v1/*`.

**Контекст.** Панель уже использовалась; SPA даёт нужный UX (поиск, теги,
bulk, discovery, карточка устройства). Полное удаление legacy сломало бы
существующие закладки/процессы.

**Следствия.**
- Две cookie/Bearer-модели: `/panel/` — подписанная cookie, SPA — Bearer в
  `localStorage`.
- Новые функции добавляются в SPA, а не в Jinja-шаблоны.
- Legacy POST не имеет CSRF-токенов (SEC-016, accepted); cookie
  `https_only=False` (SEC-017).

**Отклонено.** Немедленное удаление legacy; перенос SPA на cookie-сессии;
общий CSRF-механизм «на всякий случай».

## DEC-009. `/docs` отключены по умолчанию

**Решение.** `/docs`, `/redoc`, `/openapi.json` доступны только при
`DEV_MODE=1` или `EXPOSE_DOCS=1`.

**Контекст.** Публичная схема API раскрывает внутренние маршруты и формы;
production не должен отдавать её без явного решения.

**Следствия.** Для отладки контракта включай флаг осознанно и не оставляй
его в production. SPA и клиент от этого не зависят.

**Отклонено.** Всегда включённые docs; отдельный порт только для docs.

## DEC-010. `X-Forwarded-For` только от доверенных прокси

**Решение.** `client_ip()` использует прямой peer; XFF учитывается, только
если peer входит в `TRUSTED_PROXIES`, затем цепочка идёт справа налево до
первого недоверенного хопа.

**Контекст.** За прокси на loopback иначе все клиенты попадут в один
rate-limit bucket; без прокси доверие XFF позволяет обходить лимиты и
подставлять жертву.

**Следствия.** При неверном `TRUSTED_PROXIES` лимиты либо слишком строгие,
либо обходятся. Это конфигурационный параметр, а не «магия».

**Отклонено.** Безусловное доверие XFF; отказ от per-IP лимитов.

## DEC-011. Docker: non-root, автосекреты, публикация только нужных портов

**Решение.** Multi-stage сборка (Node → Python), UID 1000, entrypoint
генерирует/переиспользует `DEVICE_SECRET`/`WEB_SECRET` в
`/app/data/.secrets.env` (600); публикуются `8000` и `21116`, `21114` — нет.

**Контекст.** Установка «одной командой» без ручного создания секретов;
контейнер не должен работать root; API и shim — разные сетевые роли.

**Следствия.**
- При пустых env секреты создаются один раз и переиспользуются; удаление
  `.secrets.env` = новые секреты и потеря расшифровки паролей устройств.
- Без volume `data/` БД исчезает вместе с контейнером.
- Клиент с пустым `api-server` ждёт API на `21114`; нужен явный
  `api-server` или маппинг `21114:8000`.
- Docker-файлы сейчас **не в git** — это инфраструктурный пробел, а не
  свойство решения.

**Отклонено.** Root в контейнере; секреты, запечённые в образ; публикация
всех портов RustDesk «для удобства».

## DEC-012. Осознанно принятые риски

Зафиксированы в `docs/SECURITY.md` §12. Кратко: heartbeat spoof
(SEC-005), отсутствие CSRF в legacy (SEC-016), секреты Docker в env
(SEC-018), отсутствие auth на shim, UDP plaintext, отсутствие audit log,
раздельные исторические БД.

Это не «забыли исправить», а решения с известными границами. Пересматривать
их можно только вместе с изменением протокола/модели угроз, а не точечным
патчем.

## DEC-013. Heartbeat: per-device лимит + aggregate per-IP, запись в threadpool

**Решение.** `/api/heartbeat` лимитируется в два слоя:

1. `HEARTBEAT_PER_MINUTE_PER_DEVICE` (20/мин) — ключ `(device id, client IP)`;
2. `HEARTBEAT_PER_MINUTE_PER_IP` (6000/мин) — агрегатный потолок на IP.

Сначала проверяется персональный bucket; при отказе общий IP-бюджет не
расходуется. Запрос без валидного `id` ограничивается только агрегатным
потолком. `429` содержит `Retry-After`. SQLite-запись выполняется в
`run_in_threadpool` со своей сессией.

**Контекст.** Клиент шлёт heartbeat каждые ~15 с. 800 устройств за одним NAT
дают ≈3200 запросов/мин; старый лимит 300/мин на IP отклонял всё после первой
сотни. IP не идентифицирует устройство, а `id` в heartbeat не
аутентифицирован, поэтому одного ключа недостаточно.

**Следствия.**
- 800 устройств с интервалом 15 с укладываются в 6000/мин с запасом на
  реконнект; одно устройство не может вытеснить соседей по NAT.
- Подделка чужого `id` с другого IP не расходует bucket жертвы; с того же
  IP — возможна, но ограничена общим потолком (SEC-005 остаётся принятым
  риском).
- 6000/мин — не «безлимит», а конечный aggregate-cap. При росте парка или
  изменении интервала значение настраивается осознанно.
- Счётчики in-memory и per-process: при нескольких uvicorn workers лимиты
  умножатся; внешний store пока не реализован.
- Персональный bucket очищается от старых ключей не чаще раза в 60 с; при
  распределённом флуде память ограничена скоростью создания ключей на IP.

**Отклонено.**
- Поднять только `HEARTBEAT_PER_MINUTE_PER_IP` до 3200+: ослабляет защиту
  всех клиентов и не решает смешение устройств за NAT.
- Ключ только по `id`: чужой IP мог бы исчерпать bucket устройства.
- Доверять `X-Forwarded-For` без `TRUSTED_PROXIES`: обход лимитов и
  подстановка жертвы.
- Отключить rate limit или сделать его безграничным.
- Оставить синхронный SQLite в `async def`: при всплеске блокируется event
  loop и истощается пул соединений.

## DEC-014. Sysinfo: write-once + разрешение из панели

**Решение.** `/api/sysinfo` принимает отчёт и всегда отвечает
`SYSINFO_UPDATED` для валидного ID, но пишет в БД только если:

1. строки ещё нет, и ID известен панели (`address_book_entries` или
   `discovered_devices`);
2. либо строка неполная (`hostname`, `os`, `username`) и payload содержит
   недостающие поля;
3. либо есть одноразовое разрешение от кнопки «Refresh info» (heartbeat выдал
   `{"sysinfo": true}`; разрешение живёт 120 с).

`SYSINFO_PER_MINUTE_PER_IP` поднят с 60 до конечных 6000/мин. DB-запись
выполняется в threadpool со своей сессией.

**Контекст.** Штатный клиент сам шлёт sysinfo при старте и после входа
пользователя Windows, а на любой ответ, кроме `SYSINFO_UPDATED`, повторяет
каждые 120 с (`ID_NOT_FOUND` — каждые 3 с). При 800 устройствах за одним NAT
лимит 60/мин превращался в вечный retry-цикл, а каждый прошедший запрос
перезаписывал строку. Просто поднять лимит нельзя: это открывает рост БД
через случайные ID и перезапись карточек.

**Следствия.**
- После первого заполнения карточка не меняется автоматически. Обновилось
  железо/ОС — оператор нажимает «Refresh info».
- Устройство, которого нет ни в книге, ни в discovery, не получит строку,
  пока его не добавят в книгу (или пока админ не нажмёт refresh для его ID).
- Повторные отчёты стоят один `SELECT` по PK и не пишут на диск; поток
  случайных ID не создаёт строк.
- Разрешение одноразовое и живёт только в процессе: после рестарта его нужно
  запросить заново. Несколько uvicorn workers имеют независимые состояния —
  как и остальные in-memory лимиты.
- «Заполнена» означает непустые `hostname` + `os` + `username`; остальные
  поля могут быть пустыми, если клиент их не прислал.

**Отклонено.**
- Отклонять автоматические upload-ы через `429`/`ID_NOT_FOUND`: клиент
  зацикливает retry и нагрузка только растёт.
- Перезаписывать карточку при каждом отчёте: 800 устройств пишут БД на
  каждом старте, данные всё равно не меняются.
- Создавать строку для любого валидного ID при лимите 6000/мин: случайные ID
  раздувают БД.
- Хранить разрешение в БД/на диске: это одноразовое UI-действие, а не
  долговременное состояние.

## DEC-015. Display name: сервер — источник истины, клиент кэширует при входе

**Решение.** `users.display_name` правится в панели двумя путями:
администратором (`PUT /api/v1/users/{uid}`) и самим пользователем
(`PUT /api/v1/me`). Значение нормализуется (`clean_display_name`: trim +
схлопывание пробелов/переводов строк), ограничено 128 символами; пустая
строка допустима и означает «использовать логин». `/api/login` и
`/api/currentUser` возвращают сохранённое значение без изменений.

**Контекст.** RustDesk-клиент 1.4.x при успешном `/api/login` сохраняет
объект `user` в локальную опцию `user_info`
(`flutter/lib/models/user_model.dart::_parseAndUpdateUser`). При исходящем
подключении `create_login_msg` (`src/client.rs`) берёт `my_name` из:
1) локальной опции `display-name`, если она задана в клиенте;
2) иначе `user_info.display_name` (fallback — `user_info.name`);
3) иначе имя пользователя ОС.
Полученный `my_name` уходит в `LoginRequest` и отображается на удалённом ПК
(приглашение/окно подключения, аудит). Поэтому серверное имя — единственный
способ централизованно задать то, что видит принимающая сторона.

**Следствия.**
- Смена имени в панели не мгновенная: клиент применит её после следующего
  входа (обновления `user_info`). Перезапуск клиента без входа не помогает.
- Если в клиенте вручную задана локальная опция `display-name`, она
  перекрывает серверное значение — это ограничение клиента, не сервера.
- Клиент капитализирует каждое слово (`ivan petrov` → `Ivan Petrov`).
- Значение видно другим пользователям и попадает в UI принимающего ПК,
  поэтому оно нормализуется и ограничено по длине; это не секрет.
- Админ может изменить имя любому пользователю; обычный пользователь —
  только своё (роль/статус/пароль через `/api/v1/me` не меняются).

**Отклонено.**
- Отдельная таблица профилей: поле уже есть в `users` с миграции `0001`.
- Хранить имя только в `localStorage` панели: оно должно уходить клиенту
  через `/api/login`, иначе RustDesk его не увидит.
- Разрешать менять имя без ограничения длины/переводов строк: это строка,
  которая рендерится в чужом UI.

## DEC-016. UI SPA: светлая тема по умолчанию, RU/EN через свой словарь, тосты одним провайдером

**Решение.**
- Тема: `useTheme()` считает светлую тему значением по умолчанию; тёмная
  включается только явным переключателем и хранится в `localStorage`
  (`ab_theme=dark`). `main.tsx` применяет сохранённый класс до первого
  рендера, чтобы не было вспышки.
- Локализация: собственный модуль `frontend/src/i18n.tsx` — плоские ключи,
  английский словарь задаёт тип `TKey`, русский проверяется как
  `Record<TKey, string>`. `I18nProvider` хранит язык в состоянии React и в
  `localStorage` (`ab_lang`), поэтому смена языка перерисовывает всё дерево
  без перезагрузки. По умолчанию — русский.
- Уведомления: `NotificationProvider` + `useNotify()` в
  `frontend/src/notifications.tsx`. Хост один на всё приложение, `fixed
  top-3 z-[100]`, `pointer-events-none`; тост живёт 2.6 с, затем 220 мс
  анимации исчезновения. Цвет: `bg-green-700` для успеха, `bg-red-700` для
  ошибки (белый текст проходит WCAG AA).

**Контекст.** До этого каждая страница держала свой `useToasts` и рендерила
`<Toasts>` внутри `Layout`; уведомления появлялись снизу справа без анимации
и могли перекрывать нижнюю навигацию. Тексты были захардкожены по-английски,
а тема по умолчанию была тёмной (`localStorage.getItem('ab_theme') !== 'light'`).

**Следствия.**
- Любой новый текст в SPA добавляется ключом в оба словаря; пропуск в
  русском словаре ломает `tsc`, а не тихо показывает английский.
- `relTime(iso, lang)` и `statusLabel(p, lastSeen, lang)` требуют язык
  явно — это заставляет обновлять вызовы при добавлении нового экрана.
- Тосты не блокируют клики и не участвуют в потоке документа, поэтому
  всплытие не сдвигает интерфейс и не мешает работе с таблицей/модалкой.
- Legacy-панель `/panel/` не локализуется и не использует эти провайдеры:
  это отдельный server-rendered UI.

**Отклонено.**
- Тянуть `react-i18next`/`i18next` ради двух языков и ~200 строк: лишняя
  зависимость и инициализация.
- Держать тосты в каждой странице: дублирование таймеров и разное поведение.
- Оставлять тёмную тему по умолчанию: на белом фоне требование контраста
  выполнить проще, а тёмная остаётся опцией.
