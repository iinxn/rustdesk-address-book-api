# LESSONS_LEARNED — выводы, которые предотвращают повторение

Это не список инцидентов (он в `ERRORS.md`) и не архитектура (она в
`docs/project/ARCHITECTURE.md`). Здесь — короткие правила, полученные из
реальной истории проекта. Каждый пункт подтверждён практикой; если правило
перестанет быть верным, его нужно удалить, а не «дополнить исключением».

## 1. Ошибка — это данные, а не помеха

- Не увеличивай timeout/retry, пока не понял причину. `deadline has elapsed`
  в RustDesk — это отсутствие server-first `KeyExchange`, а не медленная
  сеть; увеличение таймаута лишь удлиняет ожидание.
- Не считай проблему решённой, если сообщение просто перестало
  отображаться. Проверяй фактическое состояние: порт, handshake, запись в
  БД, ответ API.
- Отделяй слои: TCP KX, UDP relay, upstream `hbbs`, HTTP API, SQLite. Один
  и тот же симптом «не подключается» может быть в любом из них.

## 2. Проверяй факты, а не догадки

- Первый шаг диагностики — точный текст ошибки, версия, порт, условия.
  Затем `/health/ready`, `ss -tlnp`, конфиг, логи, БД.
- Код и фактическая конфигурация важнее документации. В этом проекте уже
  были расхождения: `logs/app.log` не создаётся, SPA хранит токен в
  `localStorage`, порт по умолчанию — `8000`, а клиент вычисляет `21114`.
- Перед изменением смотри git-историю: возможно, решение уже принималось
  или было отклонено.

## 3. Docker собирает только то, что реально лежит в контексте

- Незакоммиченная миграция = отсутствующая миграция в образе. Именно так
  возник рестарт-луп `Can't locate revision identified by '0003'`.
- «Работает локально» не значит «попадёт в образ»: проверяй
  `git ls-files`, `docker run ... ls /app/alembic/versions/`, а не только
  рабочую папку.
- В этом репозитории `Dockerfile`/`docker-compose.yml`/`.dockerignore`
  сейчас **не в git**. Не обещай Docker-деплой с чистого клона, пока это не
  исправлено.

## 4. Миграции проверяются на копии реальной БД

- Пустая БД не показывает проблемы с существующими данными: ограничения,
  batch-пересборка таблиц, NOT NULL, конфликты уникальности.
- Обязательный минимум: backup → upgrade на копии → `PRAGMA
  integrity_check` → downgrade → снова upgrade.
- Не редактируй `alembic_version` вручную и не «пересоздавай» базу. Если
  ревизия потерялась — восстанови файл, а не номер.
- `data/base.db` и `data/pc-service.db` — разные исторические данные.
  Переключение `DATABASE_URL` без backup — потеря видимости данных, а не
  «чистка».

## 5. Не смешивай источники присутствия

- Heartbeat (`entries.last_seen`), discovery (`discovered_devices`) и
  sysinfo (`device_info`) — три независимых сигнала. Они могут расходиться,
  и это нормально.
- Discovery означает «шим видел ID в трафике», а не «это тот пользователь»
  и не «устройство в книге». Не используй его как доказательство личности.
- `online` в discovery не должен управляться heartbeat'ом, а heartbeat не
  должен создавать `device_info` или discovered-строку.

## 6. Время без таймзоны требует компенсации на границе

- Схема исторически naive UTC. Frontend обязан парсить такие строки как
  UTC (`parseUtc`), иначе UI показывает сдвиг.
- Не исправляй это точечно в одном запросе: либо миграция всех слоёв, либо
  единая граница. Полумеры создают ещё более запутанные сдвиги.
- Новые timestamps пиши в том же формате; не добавляй `Z` только в одном
  эндпоинте.

## 7. Права проверяются на каждом запросе, а не один раз в UI

- `rule` 1/2/3 и `can_write = rule >= 2` — единственный источник. Не
  доверяй `book guid`, `is_admin`, `owner` из тела запроса.
- Скрытие кнопки в SPA — не авторизация. Bulk-операции проверяют каждый ID
  отдельно; частичный успех — ожидаемое поведение.
- Ошибка доступа к чужой записи часто маскируется под `404`, чтобы не
  раскрывать существование. Это осознанно.

## 8. Секреты и сеть

- `DEVICE_SECRET` нельзя ротировать без перешифрования паролей устройств;
  `WEB_SECRET` ротировать можно (разлогинит только legacy-панель).
- Не логируй ключи, токены, пароли и содержимое `.env`. Для ключей
  допустимы только отпечатки.
- TLS terminates на прокси; приложение само отдаёт HTTP. Не открывай
  `8000`/`21116` в интернет «на минуту проверить».
- `X-Forwarded-For` доверяй только от `TRUSTED_PROXIES`, иначе лимиты
  обходятся, а жертва попадает в общий bucket.

## 9. API-контракт клиента — не «очевидный»

- `/api/*` должен сохранять формы ответов штатного RustDesk. Расширенные
  поля (`presence`, `tag_objs`, `info`, `in_books`) живут только в
  `/api/v1/*`.
- Формат ошибок различается: RustDesk-роуты — `{"error": ...}`,
  `/api/v1` — `{"detail": ...}`, Pydantic — `{"detail":[...]}`. Не смешивай
  без причины.
- ID устройства валидируется не из косметики: `@`, `/`, `?`, `&`, `=`
  могут перенаправить клиент на другой сервер/relay.
- Любое изменение контракта проверяй живым клиентом, а не только curl.

## 10. Автотестов мало — это факт, а не повод выдумывать результат

- Для heartbeat и sysinfo есть регрессионные наборы
  (`tests/test_heartbeat_rate_limit.py`, `tests/test_sysinfo_upload.py`),
  включая 800 устройств и параллельный всплеск. Запуск:
  `.venv/bin/python -m pytest -q`; нагрузочные — `RUN_LOAD_TESTS=1 ... -m slow`.
- Остальные области (auth, права книг, миграции, SPA) автотестами не покрыты;
  не выдавай наличие одного набора за полное покрытие.
- Нельзя писать «тесты прошли», если они не запускались. Минимум:
  `compileall`, импорт `app.main`, при UI — `npm run build` + `npm run lint`,
  плюс ручной smoke из `docs/development/TESTING.md`.
- Разрушительные проверки — только на временной БД и отдельном порту.
- Синтетический нагрузочный тест не доказывает production-производительность:
  фиксируй окружение, число запросов и что осталось непроверенным.

## 11. Документация — часть изменения

- Если ошибка воспроизводима — добавь её в `ERRORS.md`; если вывод
  предотвращает повторение — сюда; если это архитектурный компромисс — в
  `DECISIONS.md`.
- Не дублируй один и тот же текст в нескольких файлах: дай ссылку.
- Не выдумывай инциденты, коммиты и результаты тестов. Непроверенное
  помечай «требует проверки».

## 12. IP — не идентификатор устройства за NAT

- Один публичный IP может скрывать сотни устройств. Per-IP лимит на
  heartbeat должен быть либо очень большим, либо дополнен ключом по
  устройству; иначе первая сотня клиентов «съедает» окно и остальные
  получают `429`.
- Ключ `(device id, client IP)` даёт независимость устройств за одним NAT и
  не позволяет чужому IP исчерпать bucket конкретного устройства. Но `id`
  в heartbeat не аутентифицирован, поэтому нужен отдельный конечный
  aggregate-cap на IP — он и остаётся защитой от флуда.
- Сначала проверяй персональный лимит, потом общий: иначе один клиент с
  retry-циклом расходует общий бюджет и вытесняет соседей.
- `X-Forwarded-For` не делает IP доверенным: без `TRUSTED_PROXIES` ключ —
  прямой peer.

## 13. Синхронный SQLite в `async def` блокирует event loop

- SQLAlchemy/SQLite синхронны. Вызов в `async def` без threadpool
  блокирует цикл событий; при исчерпании пула соединений запросы ждут
  connection, а не I/O, и всплеск растягивается.
- Для массового heartbeat (>50 одновременных) это воспроизводимо: event loop
  встаёт, клиенты ретраят, нагрузка усиливается.
- Решение — `run_in_threadpool` и собственная сессия в рабочем потоке; не
  передавай один `Session` между потоками без необходимости.
- Проверяй не только среднюю частоту (`800/15с ≈ 53/с`), но и пик после
  реконнекта, когда все устройства стартуют одновременно.
- То же для CPU: bcrypt (~0,4 с) в `async def /api/login` замораживал весь
  сервер — 10 неудачных входов давали heartbeat 3,7 с (SEC-021). Тяжёлые
  CPU-операции — в отдельный ограниченный пул, а при переполнении — отказ
  (`429`), а не очередь: очередь растягивает атаку, отказ её гасит.
- Лимиты по умолчанию сверяй с размером парка: общий для TCP и UDP шима
  потолок 200 сессий был меньше штатных ~800 устройств (SEC-023).

## 14. Клиент ретраит телеметрию по-разному: 3 с или 120 с

- В `src/hbbs_http/sync.rs` ответ `ID_NOT_FOUND` на `/api/sysinfo` сбрасывает
  `last_uploaded`, и клиент повторяет попытку **каждые 3 секунды**. Любой
  другой ответ, кроме `SYSINFO_UPDATED` (включая `429` и сетевую ошибку),
  откладывает повтор на `UPLOAD_SYSINFO_TIMEOUT=120` секунд.
- Значит, `ID_NOT_FOUND` нельзя отдавать «на всякий случай»: это усилитель
  нагрузки. Для известного, но нежелательного запроса правильный ответ —
  `SYSINFO_UPDATED` (принять и проигнорировать).
- Клиент сам инициирует sysinfo при старте и после смены пользователя
  Windows; сервер не может это запретить, только не писать в БД.
- Лимит, который массово отдаёт `429`, не защищает, а создаёт постоянный
  retry-фон. Сначала уменьшай стоимость запроса (no-op), потом считай
  арифметику пика.

## 15. Имя, которое видит удалённый ПК, — это `my_name` из кэша клиента

- `LoginRequest.my_name` формируется на стороне инициатора подключения:
  сначала локальная опция клиента `display-name`, затем
  `user_info.display_name` из `/api/login`, затем имя пользователя ОС
  (`src/client.rs::create_login_msg`).
- `user_info` пишется при успешном входе
  (`flutter/lib/models/user_model.dart`). Серверное изменение `display_name`
  не долетает до уже залогиненного клиента — нужен повторный вход.
- Значит, «поменял имя в панели, а на другом ПК старое» — это не баг API, а
  кэш клиента и/или заданная локально опция `display-name`.
- Поле уходит в чужой UI: нормализуй пробелы, ограничивай длину, не считай
  его секретом и не позволяй менять чужое имя без прав администратора.
